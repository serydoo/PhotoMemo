# MemoMark 2.2.4 (101) 版本更新说明

## 版本与范围

- 版本：`2.2.4`
- 构建号：`101`
- 范围起点：`0954bea`（MemoMark `2.2.3 (100)` 版本列车起点）
- 对比范围：`0954bea..当前工作树`
- 更新性质：维护性更新与行为保持的核心架构整理。
- 当前状态：`Version Locked; Manual Acceptance Complete; Engineering Follow-ups Deferred`。

本轮将已经成型的配置、队列、媒体保存和展示代码重新归入明确的
责任边界。它不新增云端服务、不改变 Apple Photos 的原图所有权，也不
改变 Memory Engine、Layout Engine、Renderer、Export 或 Share Extension
已经接受的产品契约。

## 面向用户的变化

### 配置与编辑更连贯

- 配置中心按页面、状态和运行时职责拆分，切换记忆对象、预设、相册和
  编辑页面时，较早返回的异步结果不会覆盖当前选择。
- 记忆对象头像选择与裁切的取消、恢复和完成路径更稳定；取消编辑不会
  意外写入头像或影响当前预览。
- 首页预设、最近任务和配置页面保持现有的 Apple 原生导航与阅读层级，
  同时降低一个根视图同时承担过多状态和展示职责的风险。

### 照片处理与恢复更可靠

- 已进入处理流程的照片继续使用接收时冻结的配置快照；之后在界面中
  修改设置，不会改变正在处理照片的记忆含义或输出语言。
- 队列状态、保存回执、重试、恢复和通知职责进一步分离，处理中断后
  能继续基于同一份持久化事实判断下一步，而不是依赖临时界面状态。
- 照片保存仍然只在 Apple Photos 事务完成并可被读取后确认；原图不会
  被 MemoMark 修改。
- 静态照片与完整 Live Photo 继续遵循各自的输入、输出和配对规则，
  不会把未确认完整性的动态照片悄悄当作静态成功处理。
- 对部分 Apple Photos 分享提供者只交付静态表征、却仍标记为 Live Photo 的
  情况，时光记会先在本机确认原始动态照片身份，再沿用完整动态输出；无法
  唯一确认时会明确停止，不会把结果伪装为静态成功。

### 代码库更易长期维护

- 以应用事务、领域规则、平台适配和界面投影为主线整理内部依赖，减少
  队列、配置、PhotoKit 和根视图之间的直接耦合。
- 旧的产品阶段命名已从活跃界面与核心路径中移除；剩余的版本化名称仅
  保留在需要兼容既有持久化数据或旧源码调用的位置。
- 配套测试现在跟随拆分后的真实责任归属，而不要求新结构继续伪装为旧的
  单文件实现。

## 不变的原则

- 照片只在用户设备本地处理，不上传至 MemoMark 服务。
- Apple Photos 继续拥有原始照片；MemoMark 只生成新的输出。
- 记忆时间计算仍以照片拍摄上下文为依据，不以导出时间替代。
- Renderer 不负责业务语义或布局决策；布局与记忆含义仍由各自的既有
  引擎和契约负责。

- 配置 `2.2.4 (101)` 的 App、Share Extension、Widget、测试与 Device QA
  版本字段已统一。使用隔离 DerivedData 的无签名通用 iOS Debug 构建已通过，
  且主 App、Share Extension、Widget 产物均解析为 `2.2.4 / 101`。
- 当前相同产品代码在版本字段变更前的实体 iPhone 17 Pro Max
  `MemoMarkDeviceQA` 套件为 `17 passed / 0 failed / 0 skipped`，覆盖静态
  照片、完整 Live Photo、RAW/ProRAW、输出数量、输入保留、Live Photo
  读回和受控中断后的多次冷启动稳定性。
- `2.2.4 (101)` 已在实体 iPhone 17 Pro Max 原位重新安装，并完成一次真实
  Apple Photos Share -> Live Photo 输出 -> PhotoKit 保存读回的针对性验证：4 个
  输入均按动态路径完成，读回均确认有静态资源、配对视频、正时长和有效像素
  尺寸。用户已确认输出相册中的人工视觉与播放检查基本通过；该人工结论与
  PhotoKit 资源读回证据分开记录。
- TX-001 仍缺少 Share Extension 发起、延迟可见性、恢复中权限改变、取消
  与收据写入失败等完整矩阵证据；BP-001 仍缺少可接受的 Instruments
  测量活动。这两项不影响当前继续使用，但仍不构成正式生产认证。
