# MemoMark V4 行内模块录入形式研究

日期：2026-08-26
状态：研究完成，方案 A 已按边界实现；本轮继续统一当前胶囊表现
研究对象：Card Content Editor 中“自定义文字 + 一个或多个模块”的混排录入

## 1. 研究结论

MemoMark 当前的胶囊不是单纯的装饰，而是一个可编辑的模块对象：它需要在光标中间
插入、被当作一个整体删除、在不同 renderer 的独立区域中保存，并在输出时被解析为
照片自己的信息。基于这些约束，最稳妥的方向不是把胶囊替换成可直接编辑的字符串，
而是把“稳定的数据身份”和“编辑时的视觉表现”彻底分离。

推荐保留当前 iOS 胶囊作为主要编辑表现，并补齐以下底层契约：

1. 持久化的模块 key、参数、显示标题和组合顺序是唯一事实来源，胶囊文字只是投影。
2. 解析失败时仍保留模块对象，显示稳定的降级标记或保留名，而不是变成空白或零尺寸
   attachment。
3. 复制、粘贴、撤销、照片说明写入和 renderer 输出都使用结构化内容，不从胶囊截图或
   本地化标题反向推断模块。
4. 每种 presentation style 只读取自己的 content contract；任何新 renderer 都通过
   “可编辑区域 / 输出区域 / 照片说明来源”声明消费范围，不共享另一种样式的 slot。

这条路线可以获得网页参考中“语法失效仍可读、内容可诊断”的优点，同时保留 iPhone
上自然、直观、容易点按的编辑体验。

## 2. 当前场景的不可妥协约束

| 约束 | 录入形式必须保证的行为 |
| --- | --- |
| 混排 | 普通文字和模块可在任意顺序、任意光标位置组合 |
| 原子编辑 | 模块整体插入、选择、删除，不能被误拆成字符 |
| 局部光标 | 在模块前、模块后、自定义文字之间退格，只影响光标邻近内容 |
| 多 renderer | Classic White、Minimal 和未来 2～3 个自定义区域相互独立 |
| 输出一致 | 编辑内容、renderer 结果、Apple Photos 照片说明使用同一结构化顺序 |
| 失效可恢复 | 模块解析失败、字段缺失或版本升级后仍能看到并修复原组合 |
| 本地化 | 标题、辅助功能标签和输出值可以独立翻译，不依赖英文语法 key |
| 可访问性 | VoiceOver 能读出模块身份和当前值，不能只读出“图片”或一段乱码 |
| 高度稳定 | 空白、文字和模块状态使用同一行盒，不能因显示形式改变光标基线 |

## 3. 可选设计

### 方案 A：增强当前胶囊（推荐）

编辑区继续显示“图标 + 本地化短标题”的轻量胶囊；每个 attachment 携带稳定 module
identifier、版本、参数和可选的 resolved value。解析失败时显示同尺寸的降级胶囊，例如
“位置 · 暂不可用”，同时保留原 identifier。

优点：

- 最符合当前产品已经建立的编辑心智模型，迁移成本最低。
- TextKit attachment 天然是一个字符，适合当前的原子删除和局部光标逻辑。
- 图标和短标题能快速区分普通文字与动态照片信息；用户不需要记忆语法。
- 可以在模块胶囊内部显示失效、过期或需要重新授权等状态，而不丢失内容。
- 与当前各 renderer 的结构化 `V1ContentItem` / content contract 方向一致。

风险与补强：

- 胶囊显示文本不能作为序列化格式；必须实现结构化 copy/paste 和稳定 fallback。
- 胶囊过多时会占用横向空间，需要保留换行、滚动和紧凑标题策略。
- 必须为失效状态和 VoiceOver 增加明确语义，不能只换一个灰色颜色。

适用判断：当前 MemoMark 的首选方案；本轮代码已经沿着“统一行盒 + TextKit attachment”
继续收敛。

### 方案 B：纯语法占位符

在编辑区直接显示类似 `{{location}}`、`{{capture_date}}` 的文本，插入时由系统生成，
用户可以直接编辑或删除语法。失效时仍显示原始 key，因此诊断能力最好。

优点：

- 可读、可导出、可调试；解析失败不会让信息消失。
- 与网页截图参考接近，未来可支持高级用户手动组合变量。
- 纯文本复制、粘贴、版本迁移和文本 diff 相对简单。

风险：

- 用户可能误删一个大括号、拼错 key 或破坏参数，导致运行时失效。
- 本地化和短标题不自然，普通用户要理解实现语法。
- 纯文本光标会把模块边界交给字符编辑，当前已经解决的原子删除问题会重新出现。
- 照片说明输出不能直接信任编辑区字符串，仍需要解析器和错误恢复。

适用判断：适合调试面板、开发者模式或“查看原始组合”的辅助视图，不建议作为普通
iPhone 编辑区的唯一表现。

### 方案 C：无边框行内标记

模块显示为带小图标的短文本，例如 `⌖ 位置` 或浅色文字/底色，但取消完整胶囊边框，
让整句更接近自然文本。

优点：

- 比胶囊更轻、更省横向空间，适合模块密集的句子。
- 仍可以基于 attachment 保留原子删除和稳定 module identity。
- 视觉上更接近正文，适合 Minimal 或强调留白的未来风格。

风险：

- 模块和普通文字边界不够明显，光标靠近模块时更容易产生误解。
- 失效、选中、可删除状态的反馈较弱，需要依赖颜色之外的图标或 VoiceOver。
- 如果没有稳定的选中态，用户不容易知道这是动态值而非已经写死的文字。

适用判断：可作为 Minimal 的第二种编辑主题，但应建立在方案 A 的结构化 attachment
和降级语义之上，而不是改成普通字符串。

### 方案 D：图标徽标（Badge）

只显示图标、很短的类型名或缩写，使用圆形/小矩形徽标；点击或长按时在旁边显示模块
完整名称和当前值。

优点：

- 密度最高，适合未来 2～3 个自定义区域或同一行内模块较多的场景。
- 默认状态视觉负担低，模块数量增多时不会迅速撑宽输入行。
- 仍可用 TextKit attachment 保持原子编辑。

风险：

- 发现性较差，用户需要依赖图标记忆或额外的辅助提示。
- 不同语言和相似模块的图标必须有非常稳定的语义体系。
- 照片说明和复制到外部应用时不能只输出徽标，需要明确的文本投影。

适用判断：适合作为“紧凑密度模式”或窄屏降级，不适合作为默认唯一方案。

### 方案 E：结构化句子构建器

把内容拆成“文字段 + 模块行”的结构化列表，模块单独成为一行或一个可拖动节点，
用户通过添加、排序和编辑节点来组成最终句子；编辑区不再模拟连续文本。

优点：

- 数据边界最清晰，失效模块、排序、复制和迁移最好解释。
- 适合未来一个 renderer 有多个自定义区域、每个区域拥有不同类型节点的情况。
- 可在保存前明确预览最终照片说明文本，降低输出歧义。

风险：

- 失去“他手持 [设备型号]，在 [位置]”这种自然句子中的直接光标体验。
- 纵向空间和操作步骤增加，与当前配置中心的轻量目标冲突。
- 需要新建排序、节点焦点、键盘避让和 VoiceOver 导航模型，改动面最大。

适用判断：只在未来出现复杂条件、分支、格式化参数或长句编排需求时考虑；当前不应
为预想中的 renderer 提前替换现有编辑器。

### 方案 F：混合模式（最终演进方向）

正常编辑时使用方案 A 的胶囊；当用户进入“查看原始组合”、模块解析失败、复制到纯
文本环境或开启高级编辑时，再显示方案 B 的语法占位符。两者都从同一个结构化内容模型
投影而来。

优点：

- 普通用户获得稳定、友好的胶囊体验，高级用户获得可诊断的语法视图。
- 失效模块可以明确展示 key 和错误状态，而不是静默消失。
- 未来可以为不同 renderer 提供不同视觉主题，但不复制内容解析逻辑。

风险：

- 需要定义双向投影、语法解析错误恢复、光标映射和切换时的 selection 保留。
- 如果两个视图各自维护状态，很容易再次产生 slot 或内容不同步问题。

适用判断：作为长期演进方向；不建议在当前光标稳定性刚收口时立刻引入双编辑模式。

## 4. 方案比较

| 方案 | 混排体验 | 失效可诊断 | 原子编辑 | 本地化 | 实现风险 | 建议 |
| --- | --- | --- | --- | --- | --- | --- |
| A 增强胶囊 | 很好 | 中高 | 很好 | 很好 | 低 | 当前默认 |
| B 纯语法 | 中 | 很高 | 弱 | 中低 | 中 | 高级/调试视图 |
| C 无边框标记 | 好 | 中 | 很好 | 很好 | 低中 | 可选 Minimal 主题 |
| D 图标徽标 | 中 | 中 | 很好 | 中 | 中 | 窄屏/高密度降级 |
| E 结构化构建器 | 中低 | 很高 | 很好 | 很好 | 高 | 复杂需求再评估 |
| F 混合模式 | 很好 | 很高 | 很好 | 很好 | 中高 | 长期演进 |

## 5. 推荐落地顺序

### 第一阶段：继续使用增强胶囊（本轮完成）

- 把 module identity、display projection、resolved value 和 failure state 分层。
- 为 attachment 增加稳定的可访问性描述、结构化复制/粘贴、文本降级投影和解析失败占位。
- 插入、粘贴和删除都登记同一份 TextKit undo 快照，撤销时同时恢复内容和光标位置。
- 两种现有胶囊渲染共用同一组尺寸、边框、图标和间距度量；失效模块使用同尺寸的橙色警示胶囊，
  不会退化为空白或零尺寸 attachment。
- 保持 `RecordCardPresentationStyle.contentContract` 是 renderer 内容来源的唯一入口。
- 为未来区域使用独立的编辑会话/草稿集合，不把模块存储重新合并为共享 slot。

### 第二阶段：增加“原始组合查看”而不是第二套编辑状态

- 通过只读诊断面板显示 `{{key}}` 或结构化 JSON-like 摘要。
- 诊断面板只从当前样式、当前区域的草稿生成，不能成为另一个持久化来源。
- 当模块失效时允许用户重新选择模块，但保留原组合顺序和相邻文字。

### 第三阶段：按真实需求选择轻量主题

- Minimal 如果需要更少视觉重量，优先尝试方案 C，而不是直接改为纯文本。
- 窄屏或模块密集时再评估方案 D。
- 只有当一个 renderer 出现条件表达式、复杂参数或大量节点排序时，才评估方案 E/F。

## 6. Apple 平台依据

- Apple 的 TextKit 文本视图负责输入、选区、辅助功能、撤销、听写等系统文本能力，
  行内 `NSTextAttachment` 是适合承载自定义内容的原生机制；因此当前使用 attachment
  作为模块原子是符合平台方向的：[WWDC26 TextKit](https://developer.apple.com/videos/play/wwdc2026/370/)，
  [Enriching your text in text views](https://developer.apple.com/documentation/uikit/textkit/enriching_your_text_in_text_views)。
- Apple HIG 的 Token Field 适合把文本转成可操作 token，但文档明确说明 Token Fields
  不支持 iOS/iPadOS，因此不能把 macOS `NSTokenField` 直接作为 MemoMark iPhone 方案：
  [Token fields](https://developer.apple.com/design/human-interface-guidelines/token-fields)。
- `UISearchTextField` 虽然支持 token，但 token 被限制在普通文本之前并且主要服务于搜索，
  无法覆盖 MemoMark 中“文字—模块—文字”的任意交错组合；它可以借鉴 token 的选择和
  删除语义，但不适合作为编辑器本体：[UISearchTextField](https://developer.apple.com/documentation/uikit/uisearchtextfield)。

## 7. 当前决策状态

- 当前产品继续使用增强胶囊，不引入第二套可编辑语法状态，也不把模块降级为普通字符串。
- 方案 A 本轮已完成：`V1ContentItem` 保留结构化身份，TextKit attachment 与 SwiftUI 胶囊
  共享视觉度量；解析失败保留原表达式并显示可读的降级状态；复制/粘贴保留文字、模块、顺序
  和模块 key；结构化插入、粘贴、删除可以通过同一 undo 快照恢复内容与光标。
- 新剪贴板使用 MemoMark 私有类型，同时读取旧 PhotoMemo 类型作为升级兼容；外部应用仍获得纯文本
  投影，不会把内部 JSON 暴露为用户内容。
- 本轮没有改变 `RecordCardPresentationStyle.contentContract`、照片说明来源、slot A-D 独立性、
  Renderer、Apple Photos 输出行为或 Apple 提交相关身份。
- 方案 C/D/E/F 仍作为后续研究选项；只有真实的 Minimal 视觉需求或复杂条件/排序需求出现时再引入，
  不提前增加第二套编辑状态。
