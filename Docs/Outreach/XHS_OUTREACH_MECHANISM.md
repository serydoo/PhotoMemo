# MemoMark 小红书触达机制

状态：`V0.1 · 只读流程与逐帖回复规范`

更新时间：2026-09-12

本文定义 MemoMark 在小红书上的需求发现、上下文回复、兴趣承接和结果记录方式。
它不是自动群发方案，也不授权任何未经确认的公开评论、私信、点赞、关注、发帖或
活动发布。

## 1. 目标与边界

### 1.1 目标

找到正在真实表达以下问题的人，并用一条与原帖有关的公开回复，让对方自然了解
MemoMark（时光记）：

- 宝宝照片越来越多，不知道怎么整理或回看。
- 想记录出生第几天、满月、百天、月龄或周岁。
- 过一段时间只记得“宝宝很可爱”，想不起当时多大、发生了什么。
- 想给照片补上日期、天数、年龄或当天的一句话。
- 产假结束、成为妈妈、坐月子或婴儿期等阶段，希望留下可回看的照片记录。
- 想做成长相册、照片书或打印重要照片，但不想先整理完整个相册。
- 使用 Apple Photos，希望照片除了保存拍摄日期，也能表达它在成长中的位置。

### 1.2 不在范围内

- 不把 MemoMark 介绍成照片管理器、云端相册、普通水印工具或 AI 自动写故事工具。
- 不要求对方上传宝宝原图、完整相册、私人截图或包含身份信息的素材。
- 不把纯情绪、医疗、家庭危机或求助帖转成产品广告。
- 不批量点赞、关注、私信、复制评论或连续触达大量陌生账号。
- 不承诺当前没有真实可访问路径支持的“免费体验”、TestFlight、下载链接或兑换权益。
- 不把内部工程名、版本阶段、测试结论或未核验的媒体能力写进公开回复。

MemoMark 对外的稳定表达是：

> 给重要照片补上“拍摄时宝宝多大”，再留下“那天发生了什么”。

产品事实可以这样说：从 Apple Photos 分享照片，MemoMark 按可用的拍摄时间和用户设定的
时间信息生成新的记忆呈现；原始照片保持不变，核心处理遵循本地优先边界。具体版本、
平台、价格、下载状态和体验资格必须在发送前重新核验。

## 2. 工具与操作方式

### 2.1 采用的能力

小红书专用 `RedBookSkills` 提供以下能力：

- 登录检查。
- 首页推荐流读取。
- 关键词搜索和筛选。
- 帖子详情与评论读取。
- 一级评论、评论回复、通知/@读取。
- 内容数据读取。

### 2.2 当前首选操作面

以可见的侧边浏览器模拟操作为主：

```text
小红书首页 → 推荐 → 向下浏览 → 打开帖子 → 读取正文和评论 → 整理草稿
```

原因：侧边浏览器更容易同时看到图片、正文、评论语气、作者回复和页面实际状态。
CLI/CDP 可以作为辅助能力，但不能把 CLI 的登录结果当作侧边浏览器已经可以发送的证据。
不同页面、创作者中心和普通主页可能出现状态不一致；发送前必须以当前可见页面为准。

### 2.3 操作原则

- 每次先从首页“推荐”流开始；关键词主要用于识别和归类，不强迫流程进入机械搜索。
- 使用新鲜的页面状态。标题、作者、链接和 AX/DOM 目标会变化，不能复用过期索引。
- 页面发生跳转、刷新、弹窗或元素脱离文档后，重新读取当前页面再操作。
- 只做当前任务需要的最小浏览，不打开与 MemoMark 触达无关的个人主页或历史内容。

## 3. 触达工作流

### 阶段 A：准备

1. 确认使用侧边浏览器，不混用多个小红书自动化客户端。
2. 打开普通小红书主页，确认当前页面确实可阅读推荐内容。
3. 如果出现登录提示、验证码、异常弹窗或“操作频繁”，停止并交给用户处理。
4. 读取当前对外可用的产品事实：名称、下载路径、版本、价格、体验资格和隐私表述。
5. 本轮设定很小的候选数量，建议先处理 2–3 篇。

### 阶段 B：推荐流发现

1. 停留在“推荐”栏目。
2. 每次向下浏览一到两屏。
3. 只记录具备照片、成长、日期、年龄、相册整理或人生阶段语境的帖子。
4. 不凭标题直接写评论；标题只能作为候选信号。
5. 同一帖子只保留一个候选记录，防止重复处理。

当前关键词标签：

```text
出生 · 产假 · 当妈 · 坐月子 · 婴儿期
```

辅助标签：

```text
出生第几天 · 满月 · 百天 · 月龄 · 周岁 · 成长记录 · 宝宝照片太多
照片整理 · 相册回看 · 照片书 · 打印照片 · 给照片加日期 · 一句话记录当天
```

关键词是内容标签，不是自动发送条件。

### 阶段 C：逐帖阅读

打开候选帖子后，至少读取：

1. 标题。
2. 正文完整内容。
3. 图片中能确认的上下文，例如“出生第 96 天”“Day 157”或成长记录版式。
4. 评论区前几条评论以及作者回复。
5. 页面是否已经存在自己的评论、重复产品广告或不适合插入产品的对话。

需要判断：

- 作者是在求方法、分享方法，还是单纯记录生活。
- 对方真正的痛点是照片整理、成长记录、回看，还是其他问题。
- MemoMark 能否只补充一个准确价值，而不改变原帖话题。
- 回复后是否可能引发进一步问题，例如下载、价格、隐私或照片处理方式。

### 阶段 D：候选评分

候选同时记录“匹配度”和“触达安全性”，不只按热度排序。

| 等级 | 判断 | 动作 |
|---|---|---|
| S | 明确出现出生天数、月龄、宝宝成长记录、照片加日期或照片回看痛点 | 读取后可形成定向草稿 |
| A | 周岁相册、照片书、宝宝照片太多、成长打印需求 | 读取后通常可形成定向草稿 |
| B | 产假、当妈、坐月子等人生阶段，正文同时涉及照片或回看 | 只写轻量共鸣，避免硬推 |
| C | 只有宝宝照片或泛情绪，没有照片记录需求 | 通常不触达 |
| X | 医疗、疾病、喂养、身体恢复、家庭危机、竞品推广或明显不适合营销 | 不触达 |

热度不是触达依据。评论数少但痛点明确的帖子，可能比高热度泛内容更有价值。

### 阶段 E：生成回复

固定结构：

```text
具体共鸣 → MemoMark 能补上的一个价值 → 轻量邀请
```

每条回复只解决一个问题，不堆叠所有卖点。

#### 出生天数 / 月龄 / 成长记录

> 你这种“出生第97天 + 当天发生的小事”的记录很有感觉，过几年再翻时，照片不只是某一天拍的，也能想起宝宝当时走到了哪个成长阶段。我在做 MemoMark（时光记），也是想给重要照片补上拍摄时宝宝的月龄或天数，再留一句当天的话，原图不动，只生成一张新的记忆照片。

#### 照片太多 / 相册整理

> “照片多不可怕，没有固定的整理顺序才可怕”太真实了。宝宝照片我还会特别想留下一个信息：拍下这张照片时，宝宝到底多大。MemoMark（时光记）不是替你整理整个相册，而是可以先从重要照片开始，按拍摄时间补上月龄或天数和一句话，让以后回看时更容易想起那段成长。

#### 产假结束 / 当妈妈 / 坐月子

> 这种阶段最珍贵的，往往不只是照片本身，还有那段时间宝宝多大、每天一起经历了什么。以后再回看，如果照片里能留下当时的月龄和一句当天的话，应该会比单看日期更容易回到那段日子。我正在做 MemoMark（时光记），就是在尝试把这类时间和记忆留得更清楚一些。

#### 成长相册 / 照片书 / 打印

> 宝宝第一年的照片很值得留下，但等到周岁才整理，常常已经很难想起每张照片具体是什么阶段了。MemoMark（时光记）想做的是先把照片里的成长位置留下来，比如当时几个月、出生第几天，以及那天的一句话。之后无论继续在 Apple Photos 里回看，还是挑重要照片去打印，都会更有线索。

### 阶段 F：发送闸门

准备好草稿不等于获得发送授权。真正输入和发送前，必须重新核对：

```text
目标帖子标题：
目标作者：
目标 URL：
当前是否已有自己的评论：
最终评论文字：
```

发送动作必须得到目标特定确认，确认内容应明确到“把这些文字发到这些帖子”。
为减少打扰，每轮最多整理 2–3 篇，并采用一次性的“本批次发送”确认：确认内容中列出
每篇帖子的标题、作者、URL 和最终文字后，本批次内不再逐条重复询问。不能用“之前同意过
做小红书”替代当前批次的发送确认；如果目标、文字或批次范围发生变化，必须重新确认。

确认后：

1. 在当前帖子中点击评论输入框。
2. 输入最终文字。
3. 停在发送按钮前复核一次。
4. 点击发送。
5. 以页面中出现的评论或成功反馈为准，不能只凭点击动作认定成功。
6. 记录实际发送时间和结果。

### 阶段 G：兴趣承接

如果作者回复或主动询问，再根据问题类型处理：

| 对方反应 | 回复方向 |
|---|---|
| “是什么软件？” | 简单说明 MemoMark / 时光记的用途，给当前真实可用路径 |
| “怎么按出生日期算？” | 说明按照片拍摄时间和设定的出生日期得到月龄/天数 |
| “会不会改原图？” | 明确原图保持不变，生成新的记忆呈现 |
| “照片会上传吗？” | 使用当前版本已经核验的本地优先事实，不扩大成未经证明的绝对承诺 |
| “能免费体验吗？” | 只有存在真实可访问的体验路径时才能说明；否则诚实说明当前状态 |
| 只回复表情或表示感谢 | 不继续追发，不主动私信 |
| 明确拒绝或无兴趣 | 停止跟进 |

自有内容的评论/@回复可以通过通知页读取，但与陌生帖子触达分开记录。对方主动
询问后，才进入产品说明或体验路径，不把评论区变成连续推销。

## 4. 频率、去重和风控

### 4.1 频率

- 一篇帖子最多一条一级评论。
- 同一作者不在短时间内连续触达多篇内容。
- 每篇之间控制在约一分钟上下；这是我们的低频操作规范，不声称是平台官方规则。
- 每轮先处理 2–3 篇，观察页面状态和回应质量后再决定是否继续。
- 不同时运行多个小红书自动化会话。

### 4.2 去重

发送前检查候选记录和当前评论区：

- 本账号是否已经评论过。
- 是否已经有人表达了几乎相同的产品建议。
- 当前帖子是否已经过时或内容状态发生变化。
- 原作者是否已经明确回答了相关问题。

禁止复制粘贴同一段评论。相同价值也必须根据原帖中的具体事实重新组织。

### 4.3 立即停止条件

遇到以下任一情况，停止本轮，不强行绕过：

- 登录提示、验证码或浏览器权限请求。
- “操作频繁”“请稍后再试”或评论失败。
- 页面元素脱离文档、帖子身份无法确认或目标 URL 改变。
- 需要上传私人照片、输入账号外的敏感信息或跳转到不明链接。
- 产品事实、价格、体验资格、版本或下载状态无法核验。
- 回复会显得利用对方的疾病、焦虑、悲伤或家庭困难做营销。

## 5. 候选记录格式

候选记录只保存完成任务所需的最小信息，不保存宝宝姓名、生日、住址、学校、精确
地点、原图或私人聊天内容。

```text
发现时间：
帖子标题：
作者公开昵称：
帖子 URL：
关键词标签：出生 / 产假 / 当妈 / 坐月子 / 婴儿期 / 其他
具体场景：
可确认的痛点：
作者意图：求方法 / 分享方法 / 生活记录 / 产品咨询 / 其他
匹配等级：S / A / B / C / X
是否已读正文：是 / 否
是否已读评论：是 / 否
回复草稿：
状态：待阅读 / 待草稿 / 待确认 / 已发送 / 有回应 / 已跟进 / 不触达
发送时间：
页面结果：
后续动作：
```

## 6. 结果指标

第一阶段不追求评论数量，先验证触达质量。每轮只观察：

- 读过多少篇，多少篇真正符合 S/A 级。
- 多少篇因为正文或评论语境被排除。
- 草稿是否引用了原帖中的具体事实，而不是泛化广告。
- 发送后是否得到自然回复。
- 对方提出的是产品用途、隐私、价格还是体验问题。
- 哪类内容最容易产生有效兴趣：出生天数、婴儿期、相册整理或产假阶段。
- 是否出现重复话术、页面异常或平台风控信号。

不把曝光、点赞、评论总量直接等同于产品价值，也不把“有人点进主页”当成已经
完成体验转化。

## 7. 事实核验清单

公开回复前，只使用当前已经能证明的表述：

- `MemoMark / 时光记` 名称正确。
- 当前是否有真实可访问的 App Store、TestFlight、邀请码或等待名单。
- 当前版本和价格信息正确；没有证据就不写具体数字。
- Apple Photos 工作流表述与当前版本一致。
- 原图不修改、新结果单独保存的说法有当前实现或验证支持。
- “本地优先”不扩大成未经当前版本证明的绝对网络承诺。
- 不写“支持所有 RAW / Live Photo / Apple 设备”等绝对能力。
- 不写尚未完成的 V4 研究方向、生产认证或内部工程状态。

## 8. 机制状态与后续演进

当前机制处于 `V0.1`，先验证“推荐流人工发现 → 逐帖阅读 → 高质量草稿 → 目标特定
确认 → 低频发送 → 观察回应”的闭环。

暂不自动化以下部分：

- 自动扫描大量推荐内容。
- 自动判断敏感情绪或医疗语境。
- 自动生成并批量发送评论。
- 自动私信或自动追踪个人主页。
- 自动承诺体验资格、发放权益或发送下载链接。

只有当候选记录、发送结果和真实回应积累到足够证据后，才考虑补充更细的分类、
话术实验或只读数据汇总；不以增加自动化为目标。
